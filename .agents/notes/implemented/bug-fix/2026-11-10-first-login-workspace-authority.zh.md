# Agent Note: 首次登录工作区权限

Status: implemented

[English](2026-11-10-first-login-workspace-authority.md) | 中文

## Problem

工作区级 RLS 要求先有工作区上下文，普通成员查询才能确定工作区。已撤销的记录在这些查询中不可见，因此把可见结果为空视为新账号可能重新建立访问权限。工作区 INSERT RETURNING 还会在所有者成员记录存在之前要求 SELECT 可见性。浏览器登录可能在配置的工作区解析成功前释放会话 Cookie。

## Decision

`app.current_user_workspace_memberships()` 是无参数的 SECURITY DEFINER 函数，归 `dsh_migrator` 所有，固定 search path，且仅授予 `dsh_app_runtime` 执行权限。它读取事务级用户 GUC，返回该用户的成员历史与工作区状态，包括已撤销记录。app 服务无需在 SQL 中接受查询用户参数，就能区分空历史与不可用历史。

`PostgresWorkspaceIdentity.onboard()` 仅在成功登录后运行。用户级事务建议锁串行执行空历史检查与个人工作区创建。普通 `resolve()` 仅读取当前成员角色；显式不可用的工作区提示返回 null。会话认证仍由认证解析器负责。工作区创建分配 UUID，先插入工作区且不使用 RETURNING，再在同一事务中插入其所有者成员记录。

配置的登录身份解析必须完成后，控制器才返回浏览器 Cookie 或官方客户端凭证。解析失败使用控制器经过脱敏的可用性响应。未配置解析器的浏览器登录保留现有行为。

归档工作区不撤销现任 owner 或 admin 的成员关系。登录和刷新可为该成员建立会话，但创作接口仅在明确恢复该工作区时解析归档成员关系。更新仍受已有管理员 RLS 策略约束，只能将未删除的归档工作区设为活跃。已撤销的成员关系不适用。

## Alternatives considered

**使用普通成员 SELECT 策略。** 工作区级可见性无法区分新账号与仅有已撤销成员记录的用户，因此不能安全控制初始化。

**在普通请求解析期间创建或恢复工作区。** 这会使读取产生持久化副作用，并可能将已撤销历史转为恢复访问。登录负责显式初始化操作。

**放宽工作区 SELECT RLS 以支持 INSERT RETURNING。** 生成 UUID 可以通过所有者成员记录建立可见性，无需扩大任何策略。

## Consequences

app 角色只能发现当前用户自身的成员历史。每个请求都从数据库读取角色，会话有效性仍是独立前置条件。受限 PostgreSQL 回归证明并发初始化只创建一个工作区，不可用历史不能触发重建，其他用户不能选择该工作区，且无需放宽 RLS 就能成功创建工作区。认证回归证明配置的异步解析器失败时不释放凭证。迁移 0016 仅修复已批准的领取策略，不验证 Worker 会话过期或撤销状态。
