# Agent Note: PostgreSQL 小说草稿必须经审核后发布

Status: implemented

[English](2026-09-23-postgres-novel-drafts-and-review.md) | 中文

## Problem

AI 创作的小说数据必须可审核、按租户隔离、保留版本，并且不能修改数据库 schema。认证与小说数据共用 PostgreSQL，因此迁移所有权、运行时授权、行级安全和发布状态流转必须与应用模型一致。

## Decision

PostgreSQL 迁移为小说、人物、技能、地点、阵营、物品、剧情线、人物技能关联和通用实体关系定义固定表。Worker 没有 DDL 权限，只能写入草稿记录和草稿版本，并绑定到一个工作区、小说、用户、agent、生成任务和幂等键。人物技能关联保留独立的关系表，并拥有自己的版本历史。

审核者先保存提案和版本编辑，再批准提案。发布服务在一个事务中原位更新已审核的草稿版本、通过乐观并发控制递增实体版本，并发布提案。数据库触发器要求存在已批准提案、提案内容未被更改、生成任务一致且基础版本符合预期。提案和生成任务状态变化会追加审计事件，但不会复制提示词、认证令牌或原始错误摘要。

`@deepseek-ai/dsh-user-auth` 已提供框架无关的 `AuthHttpController` 路由，覆盖注册、邮箱验证、登录、退出、刷新、密码重置和当前用户查询。浏览器会话使用 `__Host-dsh_session` Cookie；官方客户端使用 EdDSA Access Token 和轮换 Refresh Token。Redis 限流和邮件发送仍通过注入的适配器提供。`WorkspaceAuthoringService` 负责工作区生命周期和成员操作，`ProposalReviewService` 与 `ProposalPublicationService` 负责审核者控制的提案状态、发布和回滚。

部署角色拥有数据库对象并执行迁移。运行时连接池拒绝部署角色，并在连接建立时检查数据库角色授权。事务级身份 GUC 是可信后端输入；RLS 无法防御运行时凭据被攻破或攻击者使用该凭据执行任意 SQL。

## Alternatives considered

**允许 AI 通过 DDL 创建表。** 因为这会把 Worker 权限扩大到小说工作区之外，并使应用升级、审核和回滚不安全，所以采用固定领域表保存 AI 创建的记录。

**把所有关系都放在一个多态表中。** 人物技能关联需要高效的关系约束和稳定查询路径，因此保留独立表。其他可扩展实体关系继续使用 `entity_relations`。

**只把 JSON 提案保存到审核通过为止。** 用户需要查看和编辑普通草稿记录，因此直接保存领域草稿；提案承担审核快照和发布授权职责。

## Consequences

schema 与迁移日志明确且可审查，失败或重试的生成请求在工作区内保持幂等。草稿编辑和已发布版本使用不同状态流转，回滚可以选择历史版本。PostgreSQL 集成测试仍需使用具备正式角色的临时数据库；静态测试无法证明运行时 RLS 行为或迁移执行结果。

长篇续写使用固定的大纲、章节、章节版本、摘要、世界观事实、时间线和生成上下文记录。正文不超过 1 MiB 时使用 PostgreSQL 文本，超过该大小时必须保存对象存储元数据。`0005` 加固迁移为这些记录补充生命周期字段和发布保护。用户与 agent 创作服务通过事务级 RLS 身份设置保存幂等草稿和上下文选择；持久化的上下文选择可以在浏览器或服务重启后重放。物化服务还会在进程内复用已完成结果并共享并发重试；失败尝试不会被缓存，进程重启后的安全性仍由数据库持久化幂等约束负责。当前包提供对调用方候选项的确定性排序，但不包含 LLM 适配器、对象存储客户端、自动摘要／事实抽取或 Web 审核界面。
